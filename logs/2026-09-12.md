## 今天做了什么

### 上半场 · 收尾第 5 周

**① TOP_K 3→5 对比实验**

跑之前先想清楚了一个问题：`scored[:5]` 是 `scored[:3]` 的**超集**，所以 `hit_rate@5 ≥ hit_rate@3` 是**数学必然**，不是检索变强了。多出来的 2 块在真实场景里会变成**喂给大模型的噪音**。

结果：

| 口径 | 分数 |
|---|---|
| hit_rate@1 | 0.60（12/20） |
| hit_rate@3 | 0.90（18/20）← 原基线 |
| hit_rate@5 | 1.00（20/20） |

**核心发现：没有一题的 gold 掉出前 5 名。**

也就是说——**检索器从来没有漏掉正确答案，它把对的块全捞回来了，只是排得不够前。**
这不是「召回问题」，是「排序问题」。两字之差决定下一步动什么：

- 动 `chunk_size` / 换 embedding → 提升**召回** → ❌ 召回已满分，没空间了
- 上 **reranking（重排）** → 提升**排序** → ✅ 正打在痛点上

**这解释了 `reranking.ipynb` 为什么在备选清单里**——不是「有空看看」，是数据证明的下一步。

**③ 给 evaluator 加诊断能力（改动）**

**改动的意义**：以前检索时定死 top-3，评测只能测这一个口径，想知道别的得重跑检索（重新花 API 钱）。现在**存完整榜单，评测想切几就切几**，`ranked[:k]` 一刀就够了。**这才能算出「gold 排第几名」——诊断能力是改造的全部目的。**

## 今天最大的收获

**总分会掩盖病因。**「hit_rate = 0.90」这一个数字，底下藏着两种完全不同的失败模式：排列顺序问题 + 切块边界问题。**只看总分永远诊断不出该动哪里**——必须逐题看 + 读原文。

这也是「评测器」和「诊断工具」的区别：评测器给你一个数，诊断工具告诉你**为什么是这个数**。

## ★ 今天最重要的发现：生成不可复现（评测噪声）★

### 怎么发现的

标准版 `answers.json` 和手写版 `answers.text.json` 的 **#7 答案不一样**：
- 标准版：「The provided参考资料 does not explicitly state...」（答不出来）
- 手写版：「the two complementary approaches are **mitigation and adaptation**」（答对了！）

### 排查：输入相同，输出不同

```
逐题比对 context（喂给大模型的资料）：  一致 20/20  ✅   ← 输入完全一样
逐题比对 answer（大模型生成的答案）：    一致  6/20  ❌   ← 14 题不同
```

**输入一模一样，输出却不一样 → 问题出在大模型，不是代码。**

### 实测数据（这次做对了：跑多次，不是 1 次）

| 实验 | 结果 |
|---|---|
| 同一 prompt 跑 **6 次**（temperature=0 + seed=42） | **5 种不同答案** ❌ |
| 同一段文本 embedding 跑 3 次 | **逐位完全相同**（最大差异 0.0）✅ |

**一个确定，一个不确定。**

### 为什么

- `temperature=0` 在**单机**上该是确定的，但云服务：请求被**负载均衡分到不同机器** → 浮点加法顺序不同 → 概率最高的词可能翻转
- `qwen-plus` 是**滚动别名**，服务端可能路由到不同版本
- **`seed` 参数很可能被忽略**（名字在签名里 ≠ 实现支持）

### 踩过的思维坑（记下来）

**我第一次验证只跑了 2 次**，两次碰巧撞上同一个答案，就下结论「seed 能复现」——**错的**。
**正确的验证方法**：同一个脚本 + 同一输入 + **跑 N 次（N≥5）**，数「出现几种不同答案」。**N=2 会被运气骗。**

### 对项目的意义（关键）

| 指标 | 建在什么上 | 可复现吗 |
|---|---|---|
| `hit_rate`（检索） | **embedding** | ✅ 逐位可复现 → **变化都是真信号** |
| `keyword_recall`（生成） | **大模型采样** | ❌ 每次不同 → **单个数字不可当真** |

**好消息**：主指标 `hit_rate` 是干净的（重跑检索，top-3 与原基线一字不差）。
**坏消息**：`keyword_recall` 会有噪声。

**危险场景**（第 7 周一定会遇到）：改了 prompt，分数 0.70→0.74 就高兴——**可能纯是这次抽得好**。
更糟：真改对了但分数降了，把好改动回滚了。

### 对策：先测「噪声带」

同一配置**不改任何东西**跑 3-5 次 → 得到一串分数 → 波动范围就是**噪声带**。
```
例如：0.68, 0.71, 0.70, 0.66, 0.72  →  噪声带 ≈ 0.66~0.72
以后任何改动：落在带内 = 不算数；明显超出 = 才算真改善
```
**没有噪声带，第 7 周那张「改了什么 → 分数怎么变」的表全是噪声。**

### ⑤ 读 `define_evaluation_metrics-汉化版.ipynb`（只读不跑）✅

这个 notebook 定义了三个**生成侧**指标。读完后把它们和 rag-v2 的位置逐个对上了：

| 指标 | 问的问题 | 需要什么材料 | 我的项目有吗 |
|---|---|---|---|
| **correctness（正确性）** | 答得**对不对**（和标准答案比） | Ground Truth | ✅ 有（`eval_set.json` 的 `answer`）→ `keyword_recall` 是它的廉价版 |
| **faithfulness（忠实度）** | 答案能不能**从给的资料推出来** | 生成时喂进去的 context | ✅ 有（`answers.json` 的 `context` 快照） |
| **relevancy（相关性）** | 答案**扣不扣题** | 只要问题 + 答案 | ⚠️ 能算，但不是当前瓶颈 |

**读懂的三件事**：

1. **correctness ≠ faithfulness**（这个 notebook 反复演示的核心）
   - cell 8 的例子：`3+3=?` / context 里写着「6」/ 答案「6」→ **correctness 满分，faithfulness = 0**
   - 因为 context 只是**陈述了「6」这个事实**，没给出**推导过程**——从「6 是答案」推不出「3+3=6」
   - 直白版：**答案碰巧对了，但不是你给的资料让它对的**
2. **也可以反过来**：资料本身是错的，模型照抄 → **faithfulness 满分、correctness 零分**
3. **必须一起看**：只看一个都会被骗
   - （顺带：这 notebook 有两处变量名 bug——cell 7 引用了一个被注释掉的字段、cell 9 用了没定义的变量，**跑必报错，所以只读**）

**和我项目的对齐（三层分开测）**：

```
hit_rate（0.90）      → 检索侧召回率     → 资料有没有找对
keyword_recall（待写） → 生成侧 correctness  → 答案有没有答对
faithfulness（可做）   → 生成侧稳定版     → 答案是不是资料给的
```

**这样分工，出问题时才能定位到底是「检索的锅」还是「生成的锅」。**

### 今天理清的几个概念（都是提问问出来的）

1. **recall 就是我的 `hit_rate`**：召回率 =「该找到的找到了多少」÷ 总数
   - 它有个搭子叫 **precision（精确率）** =「捞回来的里面有多少是相关的」
   - **我测了 recall，从没测过 precision**——这是评测集的一个缺口
2. **`eval_set.json` 的 `answer` 是什么**：就是 **Ground Truth（标准答案）**，第 4 周我自己手写的
   - 为什么写得那么像原文原句？因为 `make_gold_chunks.py` 要拿它去 chunks 里**做字符串包含匹配**（`if answer in chunk_text`），改写过的答案就找不到所在块了
   - **一个字段三份用**：① 找 gold_chunks 的锚点 ② correctness 的标准答案 ③ 出题时的参考
3. **faithfulness 的 context 从哪来**：就是**生成时真正喂进去的那几块**（top-k 的全文，**不是只取一块**）
   - 所以 `answers.json` 才要存 `context` 快照——**忠实度必须拿「当时给的那份材料」来验**，事后重新检索可能就不一样了

## ★ 另一个大认知：gold_chunks 是「尺子」，不是「食材」

**我的问题**：`gold_chunks.json` 里存的就是「标准答案在第几块」，既然现成有，为什么不直接喂给 generator，省得 top_k 去找？

**答案：因为那就是作弊（数据泄漏）。**

- **gold 是给批卷老师的，不是给考生的。** generator / retriever 是考生，喂它 gold = **考前泄题**
- **真实场景根本不存在 gold_chunks**：用户问「退货政策是什么」，没人会递张纸条说「答案在第 47 段」——**系统必须自己找**。**"自己找"这件事本身就是 RAG 的价值**
- **喂了 gold 会怎样**：
  - 检索环节被彻底架空 → `hit_rate` 永远 1.00 → **这个指标直接死了**
  - 测出来的只剩「大模型会不会读文章」，跟 RAG 毫无关系
  - 做的检索 / 切块 /（未来的）reranking **全部白费**
- **gold 的正确用法只有一处**：`evaluator.py` 里拿它**对账**——「实际检索到的」对「应该检索到的」

| 模块 | 用 gold 吗 | 角色 |
|---|---|---|
| `make_gold_chunks.py` | 生成它 | 生产尺子 |
| `retriever.py` | ❌ | **考生（必须自己找）** |
| `generator.py` | ❌ | **考生** |
| `evaluator.py` | ✅ | **批卷老师** |

**这个坑有名字：「数据泄漏」（data leakage）**——ML 里最经典的一类错误：**不该看到答案的那一环看到了答案**，分数就虚高，而且虚得毫无意义。我是**在自己的项目里撞上它的**，比背定义扎实得多。

**（进阶，知道就行）什么时候可以故意喂 gold？** 做 **oracle 测试**——假设检索完美，看生成还行不行：
- 给对资料**还是答不好** → 问题在 generator / prompt
- 给对资料**就答得好** → 是检索拖累的
- **这是诊断工具，不是产品功能**（好比医生做"假设血压正常"的检查来定位病因，不是让你以后都假设血压正常）
