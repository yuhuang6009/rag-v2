## 一、★ 澄清：两次运行的区别

### 混淆点

`answers_multirun.json` 里每题存了**多个答案**，看起来像「记录了多个配置」。
**不是的** —— 那个维度是**「第几轮」**，不是「第几套配置」：

```json
{"id": 1, "question": "...", "context": "...",
 "answers": ["答案A","答案B","答案C","答案D","答案E"]}
              ↑ 这是【同一配置跑了 5 轮】的 5 个答案
```

**实测：那里面【没有任何配置字段】：**

```
每题字段：['id', 'question', 'context', 'answers']
→ 有没有 chunk_size？ 没有
→ 有没有 top_k？      没有
```

**它是「匿名」的** —— 光看这个文件，说不出它是 cs=400 还是 cs=800 的。
**因为生成它的时候（9/15）只有一套配置**（cs=800，还没开始扫参），所以没必要记。

## 二、★ 下次实验设计：避开混杂因素

### 原提议有混杂

```
A：cs=400, top_k=2   →  2 × 400 =  800 字符
B：cs=800, top_k=3   →  3 × 800 = 2400 字符
                ↑ 差了三样：cs、top_k、总字符数
```

**三个变量一起变** → 如果 A 分数低，**说不出**是「块太小」还是「上下文太少」还是「块数太少」。

> **⚠️ 这和 `choose_chunk_size` 那个 notebook 踩的是同一个坑：**
> ```
> 它：固定 top_k=5，变 chunk_size → 总字符数 640 → 1280（自己没意识到）
>    → "cs=256 更慢" 这个结论【必然成立，零信息量】
> 我：变 cs 的同时也变了 top_k 和总字符数 → 同样是混杂
> ```

### 改成 3 个配置，2 个干净对比

```
① (400,160) top_k=2    →   800 字符   ← 最省
② (400,160) top_k=6    →  2400 字符  ┐
③ (800,160) top_k=3    →  2400 字符  ┘ 总字符数相同
```

| 对比 | 变的是什么 | 回答的问题 |
|---|---|---|
| **② vs ③** | **只有 cs**（总字符都是 2400） | **cs=400 对生成有害吗？** ← 受控实验 |
| **① vs ②** | **只有 top_k**（cs 都是 400） | **喂 800 字符够不够？** ← 成本问题 |

**两个都是单变量对比，而且第 7 周要调的 `top_k` 顺便测掉了。**

**② vs ③ 完全对应检索侧做过的那次**（等字符量：`(400,160)` top_k=6 → 1.00 vs 其他 0.90）。
**同一把尺子，换到生成侧再量一遍。**

> ⚠️ 「名义 2400 字符」≠「2400 个不重复字符」（overlap 会重复）。
> `(400,160)` 若块相邻，实际只有 1600 个不重复字符，比 `(800,160)` 的 2080 少
> —— **这对 ② 不利，所以 ② 还赢的话结论更硬**。

## 三、★ 怎么衡量「两个配置谁更好」

### 第一层：检索引擎和问答产品的分界

```
检索侧（hit_rate）      是【必要条件】，不是充分条件
生成侧（keyword_recall）才是【最终指标】

检索不到 → 答案几乎不可能对（必要条件）
检索到了 → 也不保证答对（不充分）
```

**「赢了检索、输了生成」是真实存在的 —— 它叫「上下文碎片化」：**

```
cs=400 切得细 → 检索更准（每块话题纯）
              → 但每块只有 400 字符
              → 答案若横跨两块，模型可能【拼不起来】
              → keyword_recall 掉
```

**`hit_rate` 测不出这个 —— 这就是必须真跑生成侧的原因。**

### 第二层：判决靠噪声带

```
"分数差多少才算真的差？"  →  噪声带就是那把尺子
```

```
                       分数差异
                    ┌──────────────┐
   在噪声带内        │  抽签，不算数  │  → 两个配置【一样好】
                    ├──────────────┤
   超出噪声带        │  真差异        │  → 判它赢
                    └──────────────┘
```

**具体例子（噪声带宽度 0.033）：**

```
(400,160) top_k=2  →  0.72    比基线低 0.03  →  噪声带内 → 【不能下结论】
(400,160) top_k=2  →  0.62    比基线低 0.13  →  超出     → 【真的掉了】
            ↑ 同样是「掉了」，结论完全不同
```

> **没有噪声带，这两个数字分不出来。**
> **这就是「每个配置各自重测噪声带」这条规矩不能省的原因。**

### 第三层：决策（掉了 ≠ 淘汰）

```
(400,160) top_k=2：keyword_recall 0.72（掉 0.03，噪声带内）
                 成本 800 字符（省 2/3 token）
→ 「代价测不出来，但省 2/3 的钱」→ 该选它

(400,160) top_k=2：keyword_recall 0.62（真掉 0.13）
→ 「省 2/3 的钱，但质量明显下降」→ 看产品能容忍多少
```

> **这就是 `choose_chunk_size` 里 `response_time` 想说的那件事，
> 也是「调参」和「工程决策」的分界线。**
> （具体怎么算，等真数据出来再算 —— 现在没数据，讲了是空的。）

### 💰 省钱的走法：便宜筛选 → 贵确认

```
完整测（单次 + 5 轮噪声）：3 个配置 × 20 题 × 6 = 360 次生成调用
```

**建议两步：**

```
第一步（便宜）：3 个配置各跑 1 次 = 60 次调用
   → 看差异多大
   → 差异明显（> 0.05）→ 直接下结论，噪声带都不用测
   → 差异模糊（两配置差 < 0.05）→ 进第二步

第二步（贵）：只给【纠结的那两个】测噪声带 = 2 × 100 = 200 次
```

**理由**：噪声带是为了判「差异算不算数」—— **差异明显时不需要它**。
9/15 测出的宽度只有 **0.033**，说明**这个指标的噪声很小，很多差异会明显超出。**

```

┌─ 切分大小 cs ───────────────────────────────┐
│  检索侧  ✅ 9/18 跑完（(400,160) 全胜）       │
│  生成侧  ← 下次，就是 ② vs ③（等字符量对比）  │
└─────────────────────────────────────────────┘
┌─ top_k ────────────────────────────────────┐
│  只有生成侧                                  │
│  ← 下次顺便测掉：① vs ②（cs 都是 400）        │
└─────────────────────────────────────────────┘
┌─ prompt 模板 ───────────────────────────────┐
│  只有生成侧                                  │
│  ← 【之后单独做】                            │
└─────────────────────────────────────────────┘
```

**为什么 prompt 要单独做：**

```
改 cs / top_k → 只换【参数】
改 prompt     → 要换 PROMPT_TEMPLATE 那段【文字】甚至加个 --prompt 参数
              → 是代码改动，不是参数改动
```

**而且 prompt 是最干净的实验：**

```
改 prompt → 答案变了 → 分数变了
但【检索侧完全不受影响】（D1 第 9 题答对的那个）
→ 所有配置不动，只动一段文字 → 天然单变量
```

**⚠️ 但现在 `generator.py` 还没法传 prompt** —— `PROMPT_TEMPLATE` 是写死的常量。
到时候要么加 `--prompt` 参数，要么加版本号。**这是后面要写代码的地方。**

## 五、⚠️ 顺手查到一个代码缺口

```python
def run_noise(top_k, runs):
    """同一配置跑 runs 轮 → answers_multirun.json（给噪声带用）。"""
    results = generate_all(top_k, runs=runs)
    with open(NOISE_JSON, "w", encoding="utf-8") as f:
        json.dump(results, f, ensure_ascii=False, indent=2)
    print(...)
    return results
    # ← 没有写 gen_config.json！
```

**`_run()` 写了 `gen_config.json`，`run_noise()` 没写。**

**后果**：跑 `generator.py --runs 5` 测噪声带时，`gen_config.json` **不会更新** ——
它里面还留着上次单次运行的值（或者根本不存在）。

**为什么现在还没炸**：`--record` 只在模式一（读 `answers.json`）里，`--noise` 模式不记账。
**两条路暂时没交叉。**

> **⚠️ 但如果以后要把噪声带也记进账本**（9/21 log 提过这个缺口），
> **这个洞必须先堵** —— 否则记下的配置是错的，又是那个「静默 + 看起来正常」的形状。
