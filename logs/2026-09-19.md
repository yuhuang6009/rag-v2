### ⚠️ 三处理由要纠正

#### 纠正 1（#1）：`chunks.json` 的理由里有一个事实错误

**原答**：「检索侧它会被 `evaluator.py`, `make_gold_chunks.py`, `retriever.py` 需要」

**实测**（`grep -ln CHUNKS_JSON src/*.py`）：

```
读 chunks.json 的：generator.py / make_gold_chunks.py / retriever.py
                   ↑ 没有 evaluator.py
```

`evaluator.py` 的路径常量只有四个，**全都不含 chunks.json**：

```python
GOLD_JSON      = gold_chunks.json
RETRIEVAL_JSON = retrieval_results.json
CONFIG_JSON    = chunk_config.json
SWEEP_JSON     = sweep_results.json
```

**为什么会这样（这一点比记名录重要）**：

```
evaluator.py 只跟【块编号】打交道 —— 比的是 [2,0,7] 里有没有 gold 的 [0]
它【不需要看块里写了什么字】

→ 所以它读不到 chunks.json 是【故意的】，不是遗漏。
→ 这也解释了「存 gold_rank 不存原文」：编号就是它需要的全部信息。
```

> **顺带**：用「谁读它」当判据本身是**较弱的判据**（这次侥幸全对）。
> 我要求的是「影响块排第几，还是影响答案写成什么」——
> **「谁读它」会漏掉「一个脚本读自己写的文件」这种情况（见纠正 2）。**

#### 纠正 2（#3）：`vector_store.json` 不是备份，是**省钱的缓存**

**原答**：「它是由 retriever 产出的，但是我没有看到他被使用好像，他是一个备份的感觉吧」

**实测**：**它被读，而且是被「写它的那个脚本」自己读。**

```
retriever.py:49    store = json.load(open(STORE_JSON))     ← 非 --rebuild 时，直接读缓存
retriever.py:113   store = json.load(open(STORE_JSON))     ← --no-build 模式
retriever.py:28    STORE_JSON = vector_store.json   # 缓存块向量，避免重复调 API
```

**它的作用：114 个块的向量一旦算过就存下来，下次不用重算。**

```
没有它 → 每次跑 retriever 都要重新 embedding 114 个块 → 每次都花 API 钱
有它   → 切块没变时，0 成本
```

**★ 为什么这一条特别值得记**：

```
你找「谁读它」时，看了【别的脚本】 →
  evaluator 没读、generator 没读、keyword_recall 没读
→ 于是判断「没人用它，是个备份」

但读它的是 retriever.py 自己。
```

> **一个文件的读者，可能就是写它的那个脚本。**
> 「我看了几个文件没看到它」→ **这只说明你查的那几个没读，不说明没人读。**

**而且这条有一个正面教学**：`--rebuild` 这个开关存在的全部意义，就是
**「什么时候可以信任这个缓存」**——切块变了，缓存就失效，必须重建。
（和纠正 3 讲的「失效 vs 被改」是同一件事。）

#### 纠正 3（#12）：MISS 和「缝合块」是两件事，我混了

**原答**：「他主要是因为 切块的内容横跨 多个不同的部分导致的」

**这个描述其实是「缝合块」，不是 MISS。** 两者都跟块边界有关，但是**不同的故障**：

| | **MISS** | **缝合块** |
|---|---|---|
| 现象 | 答案**没完整落进任何一块** → `gold_chunks = []` | 一个块混了两个话题 |
| 后果 | ★ **比较直接失效**（分母是 20，这题永远算失败） | 排名**变差**，但分数仍然有效 |
| #07/#08 属于哪个 | ❌ **不是** —— 它们的 gold 是 `[15]`，有块 | ✅ 是 |
| 怎么发现 | `make_gold_chunks.py` 会打印 `MISS: [...]` | 看块的**开头**写了什么 |

```
MISS   ：是关于【标注】的 —— 答案切不进去，这题【测不了】
缝合块 ：是关于【向量质量】的 —— 能测，但【排得低】
```

> **两个都会让人误以为「检索变差了」，但只有 MISS 会让数字本身失去意义。**

### D3 · 手写 `gold_rank()`（待做，20 分钟）

写进 `rag-v2-src-手写练习/evaluator-手写.py`（**新加函数，不动已有的**）。

→ **`gold_rank` 是新函数，正好没练过，闭卷写一遍。**

**规格（接口）：**

```
gold_rank(ranked, relevant)

ranked   —— 一个 list，一题检索出来的【完整】排名（114 个块编号）
            例：[37, 36, 15, 2, 8, 91, ...]
relevant —— 一个 list，这题的 gold 块编号
            例：[36]   或   [9, 10]   或   []

返回：一个 int（1 开始的名次），或者 None
      = relevant 里任意一个编号，在 ranked 里【最早出现】的位置
        一个都没出现 → None
```

**四个自测用例：**

```python
ranked = [37, 36, 15, 2, 8]

gold_rank(ranked, [36])      →  2
gold_rank(ranked, [9, 10])   →  None
gold_rank(ranked, [])        →  None
gold_rank(ranked, [8, 37])   →  ?   ← 两个都在，该返回几？为什么？
```

**第 4 个是关键**：`relevant` 有两个 gold 块时，返回**最靠前**还是**最靠后**的？
（决定 `hit_rate` 是宽松还是严格。先自己决定，再写。）

**写完回答两问：**

- **A**：`gold_rank()` 返回 `None` 意味着什么？（一句话，**别用 MISS 这个词**）
- **B**：为什么存 `gold_rank` 就够，不用存 `hit_rate@1/3/5` 三个数？
