## 三、任务 A 改了什么

| # | 位置 | 改动 | 作用 |
|---|---|---|---|
| 1 | 函数签名 | `runs` 变必填参数，**不给默认值** | 漏传 → `TypeError` 当场炸 |
| 2 | `config["runs"] = runs` | 写在 `config.update()` **之后** | 把戳里的假 runs 盖掉 |
| 3 | 两个调用点 | 噪声传 `len(scores)`、单次传 `1` | 真相源 = 调用者 |
| 4 | `tag = f"{runs} 轮"` | 删掉走不到的分支 | 清理死代码 |

**★ 第 2 条的位置是成败关键** —— 写在 `update()` 上面就前功尽弃（戳会反过来盖掉参数）。
这种「顺序决定成败」的地方，是这类 bug 的常见藏身处。

**★ 第 1 条的设计原则：能报错就不要给默认值。**

```python
def record_sweep(avg, rows, runs, band=None):     # ✅ 必填
def record_sweep(avg, rows, runs=1, band=None):   # ✗ 默认值会把漏传吞掉
```

默认值看着更"方便"，实际是把「响亮地失败」换成「静默地出错」——
而静默正是这一族 bug 的全部杀伤力所在。

## 四、★ 怎么验的（今天最大的方法论收获）

### 4.1 静默的 bug 不能靠「正常用一遍」来验

```
正常用的时候，它多半是对的：
  generator --runs 5  →  戳 r5  →  --noise --record  →  戳5 = 数据5  ✅ 碰巧对
  generator           →  戳 r1  →  --record          →  戳1 = 数据1  ✅ 碰巧对

只在【换了模式、但没重新生成】的那一刻错 ——
而那一刻错得完全静默：数字正常、config 正常，只有「它俩不是一对」不对，
账本上没有任何一处会显示这个事实
```

**→ 必须【故意造出那个错配场景】再测：戳冻在 runs=5，直接记一条 1 轮的结果。**
（验证脚本演的正是 9/27 事故的那一瞬间，不需要 ①②③ 的铺垫。）

### 4.2 沙箱：不为了测「刀快不快」先划自己一刀

```python
kr.SWEEP_JSON = sandbox / "sweep_results.json"       # 把模块眼里的路径换掉
kr.GEN_CONFIG_JSON = sandbox / "gen_config.json"
kr.CONFIG_JSON = sandbox / "chunk_config.json"
```

`record_sweep` 里写的 `SWEEP_JSON` 是模块**全局变量**，调用时才去查 —— 改掉它，
函数就只看得见临时目录，真 `data/` 物理上够不着。

### 4.3 ★ 阴性对照：证明这个测试【本来是会失败的】

```
只验「新代码通过」        →  测不出假阳性（一个什么都通过的测试，看着也像成功）
新代码通过 + 【旧代码失败】 →  才证明测试抓的是那个 bug 本身
```

把修复前的旧逻辑原样搬进沙箱跑同一个测试：

```
新代码 → 8 个 [OK]
旧代码 → 沙箱账本 1 条（不是 2 条）、runs=5（不是 1）
         [FAIL] 单次的把 5 轮的【吃掉了】
         [FAIL] 被记成了 5（戳里写什么就是什么）
```

**→ 那 8 个 [OK] 的含金量，全部来自「旧代码在这里是 FAIL」。**

**这个手法可迁移**，以后改任何一行修复都可以问自己一句：

> **「我不改，它会红吗？」如果不会，那这个"验证"只是在给自己鼓掌。**

### 4.4 结果

```
测试1  runs 由调用者给，戳不许当真相源     [OK][OK]
测试2  忘传 runs 当场 TypeError          [OK]
测试3  闸门：前三行拦住错配 / 最后一行放行  [OK][OK][OK][OK]   ← 重点
测试4  真账本 8 条 -> 8 条，没动          [OK]              ← 有证据，不是"我觉得没动"
```

**测试3 的最后一行最重要**：

> **只会拦的闸 = 拦所有东西的闸 = 没用。能分辨，这闸才算装上了。**

## 七、★ 概念澄清：轮 / 生成 / 记账（三个词，别混）

今天最大的一个困惑在这次澄清上。

```
一【轮】(round)   = 20 道题各答一遍
一次【生成】       = 一条 generator.py 命令 → 1 个产物文件 + 1 枚戳
一次【记账】       = 一条 --record 命令    → 账本里 1 条记录
```

**所以 `--runs 5` 是：**

```
一次生成
  ├─ 20 题 × 每道答 5 遍 = 100 次 API
  ├─ 产出 1 个文件 answers_multirun.json
  ├─ 写 1 枚戳 gen_config.json {runs:5}
  └─ 记账时记 【1 条】(runs=5)          ← 不是 5 条！
```

**「轮完一次记一次」这个理解是错的。**
5 轮是**同一配置下的 5 次抽签**，账本要的是「这个配置的成绩」→ 合成 1 条。
`keyword_recall` 从那 1 个文件里把 5 轮分算出来，取均值 + 上下界，装进那 1 条。

**所以「一轮之内的戳全都是同一个配置」是对的，而且无害。
问题从来不在一次生成内部，在【两次生成之间】。**

### 9/27 事故按时间铺开

```
#  命令                                     产物       戳          账本
────────────────────────────────────────────────────────────────────────────
①  generator.py --top-k 2                  answers    {k2,r1}      —
①  keyword_recall.py --record              —          —           (2,1)  ✅
②  generator.py --top-k 2 --runs 5         multirun   {k2,r5}      —
②  keyword_recall.py --noise --record      —          —           (2,5)  ✅
③  keyword_recall.py --record   ★没跑生成   —          —           分数取①的
                                                                    runs取戳的5
                                                                    → 覆盖② ⚠️
```

**③ 的特征就一条：它没有跑生成。**
