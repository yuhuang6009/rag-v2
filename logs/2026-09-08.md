### 三个 json 各自是什么、谁产出

| 文件 | 里面有什么 | 谁产出 |
|---|---|---|
| `chunks.json` | 114 块 `{index, text}` | chunker.py ① |
| `gold_chunks.json` | 每题 `{id, chapter, question, gold_chunks}` | make_gold_chunks.py ② |
| `retrieval_results.json` | 每题 `{id, question, retrieved}` | retriever.py ③ |

关键：**这三个 json 里的编号，全指向 `chunks.json` 的 `index`**。这是整个评测能对上号的基石。chunker 给每块发身份证号，后面谁都认这个号。

### 两个最容易绕晕的点（我卡过的地方）

**1. relevant 和 retrieved 是两条独立路径，不是从同一份文件读的。**

```
relevant（每题的标准答案位置）  ← 拿【答案文本】去 114 块里找，落哪块就记哪块
                                    = make_gold_chunks.py ②（静态，做一次就行）

retrieved（每题检索到的 top-3）  ← 拿【问题文本】转向量，和 114 块向量算相似度
                                    排序取前 3 = retriever.py ③（动态，每次跑）
```

两条路互不知道对方。relevant 不知道 retrieved 会捞到什么，retrieved 也看不见 gold_chunks.json。**它们唯一的共同点是都引用同一套 chunk 编号**，所以最后才能拿 `36 in [36,12,88]` 去比。

**2. hit_rate 不需要「把文本映射成编号」——编号本身就是比较的元素。**

`找交集.py` 里手写的 hit 已经够用：

```python
def hit(retrieved, relevant):     # retrieved=[36,12,88], relevant=[36]
    for i in retrieved:            # 逐个看检索到的编号
        if i in relevant:          # 是不是标准答案所在块
            return True
    return False                   # 找完都没有 → 没命中
```

retrieved 和 relevant 里存的**本来就是 chunk 编号**，不是文本。所以「从列表元素映射到 chunk 编号」这个担心不存在——第③步让检索器吐编号（而不是只吐文本），hit 直接比编号即可。

### 用第 12 题走一遍真实数据

第 12 题：*What are two economic costs of climate change mentioned in the document?*

```
② 的 gold_chunks  → [36]      ← 答案句子落在 chunk #36
③ 的 retrieved    → [37,36,15] ← 检索器认为最像的 3 块
④ hit 判断        → 36 in [37,36,15] → True → 第12题命中 ✅
```

为什么 chunk #36 会进 retrieved？因为**装着答案的那块，语义上本来就最像问题**——#36 里正好有 "The economic costs of climate change include damage to infrastructure..."，问题问的就是 economic costs。检索器靠向量相似度把它捞上来了，不是和 gold 串通。

（上面 `[37,36,15]` 是真实跑出来的结果，不是编的。gold 36 排在 top-2，说明检索器找对了，只是没排第一。）

## 今天的一个教训：标准答案必须逐字，不能自己改写

我当初写 eval_set 时凭理解「改写」了 12 个答案，只验证了「关键词能搜到」，没验证「逐字是原句」。后果：

- 改写的答案（`...have significantly contributed...`）去文档里按原样定位会**错位**，因为原文夹着 `Over the past century, human activities, particularly...` 这些词
- 标注 gold_chunks 靠「答案文本在 chunk 里子串匹配」——答案不是原句 → 匹配不上 → ground truth 标不出来

**评测数据的铁律：标准答案 = 原文摘录，逐字不差（标点、大小写、连字符原样）。** 这也回头验证了 9/6 学的「标准答案 = ground truth = 尺子」——尺子刻度都对不齐，量什么都不准。

## 切块参数实验（提前踩了第 7 周 choose_chunk_size 的坑）

chunker 一开始用 chunk_size=500，切完发现 **4 题答案被切块边界拦腰切断**（答案跨在两块中间，任何单块都不含完整句子）。这就是语义单元被硬切。于是跑了个实验：

| chunk_size | overlap | 完整落块 |
|---|---|---|
| 500 | 100 | 17/20 |
| 600 | 120 | 19/20 |
| **800** | **160** | **20/20** ← 够用的最小 |
| 1000+ | 200+ | 20/20（但块越大越糊） |

**结论：chunk_size 不是越大越好，够用最小。** 800 是让 20 题都完整落块的最小值。块太大，单块 embedding 装的东西太杂、向量「糊」，检索区分度下降。所以参数区定 `CHUNK_SIZE=800, CHUNK_OVERLAP=160`（overlap≈20%），第 7 周调参实验就是改这里再重跑整套。
