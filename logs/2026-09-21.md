## 二、D2 答案：A/B 两列 + API 钱

### 核心破题：`A` 和 `B` 是两件独立的事

```
A 列：「跑了吗」      → 这个脚本【会不会被执行到】
B 列：「还对得上吗」  → 产物说的【还是不是现在的事实】
```

扫参跑的是四步：`chunker → make_gold_chunks → retriever → evaluator`。

| 脚本 | 产物 | **A 会被重写吗** | **B 还对得上吗** |
|---|---|---|---|
| `chunker.py` | `chunks.json` / `chunk_config.json` | ✅ 会 | — |
| `make_gold_chunks.py` | `gold_chunks.json` | ✅ 会 | — |
| `retriever.py` | `vector_store.json` / `retrieval_results.json` | ✅ 会 | — |
| `evaluator.py` | `sweep_results.json` | ✅ 会（**追加**，非覆盖） | — |
| **`generator.py`** | `answers.json` / `gen_config.json` | ❌ **不会** | ❌ **失效** |
| **`keyword_recall.py`** | `sweep_results.json`（生成侧） | ❌ **不会** | ❌ **失效** |

**9/18 答错的就是下面两行。**

### ★ 关键：这里是**三种**状态，不是两种

```
① 会被重写            → 自动保持有效（chunks / gold / vector / retrieval）
② 不重写，也不失效     → eval_set.json  ← 没改题目，它就一直有效
③ ★ 不重写，且失效     → answers.json / answers_multirun.json / gen_config.json
```

**第 ③ 类是唯一的危险区** —— 它躺着不动、看起来完全正常，但说的已经不是现在的事了。

**而这正是扫参流程的代价：**

```
generator.py 要花 API 钱  →  扫参【故意】不跑它
                         →  answers.json 静默失效
```

> **为什么扫参是「检索侧-only」的**：不是不能测生成侧，
> 是「每换一个 chunk_size 就重跑 20 次生成」钱受不了。
> **代价就是这个静默失效。**

### API 钱（实测）

```
retriever.py   5 处调 API  ← 块向量(114 次) + 每题问题向量(20 次)
generator.py   2 处调 API  ← 20 题生成
其他 4 个       0 处
```

**但两者贵贱差得很远**：embedding 便宜，**生成是贵的那个**（输出 token 多）。真正要省的只有 `generator.py`。

**顺带一个设计点**：`vector_store.json` 缓存让 `retriever.py` 不带 `--rebuild` 时**只花 20 次**（问题向量），省掉 114 次（块向量）。**这就是「省钱的缓存」在钱上的样子。**

## 三、★ D3 批改：off-by-one —— 今天最有价值的 bug

### 你写的代码

```python
def gold_rank(ranked, relevant):
    ranks=[i for i,idx in enumerate(ranked) if idx in relevant]
    return min (ranks) if ranks else None
```

**语义全对** —— 而且 `min` 正确表达了「最早出现 = 最宽松」这个取舍（第 4 个用例的关键）。

**但 `enumerate(ranked)` 从 0 开始，规格要求「1 开始的名次」。**

```
用例             期望    你的版本    正确版本
[36]              2        1  ❌      2
[9,10]         None     None  ✓    None
[]             None     None  ✓    None
[8,37]            1        0  ❌      1
```

**修法一个字符：**

```python
ranks=[i for i,idx in enumerate(ranked, 1) if idx in relevant]
#                                        ↑ 补这个
```

（已改 ✅）

### ★ 为什么这个 bug 比看起来严重

拿真实数据（cs=800 那批）算：

```
         正确      少1的版本
hit@1    0.60  →   0.85   ← 虚高 0.25
hit@3    0.90  →   0.95   ← 虚高
hit@5    1.00      1.00
```

**因为 `hit@k ⟺ gold_rank ≤ k`，少 1 等于把「第 2 名」当成「第 1 名」→ `hit@1` 悄悄变成了 `hit@2`。**

**三个特征全中：**

```
① 方向错：数字【变好看】了 —— 和 9/18 那个静默 bug 一样，你不会去查
② 完全静默：不报错，不警告，跑得通，结果看着很合理
③ 语义正确但数值错：连「读一遍代码」都发现不了 ——
   min(ranks) 逻辑没错，错的是【起算点】，藏在 enumerate 的默认参数里
```

> **这是今天第三次「名字/位置相近但角色不同」的陷阱：**
> ```
> keywords vs keyword_recall     （名字像，不是一回事）
> hit      vs hits               （同一个词，两侧含义不同）
> 0-based 名次 vs 1-based 名次    （← 这个是自己踩进去的）
> ```
>
> **前两个是「问出来的」，这个是自己踩的 —— 说明这个坑不是靠「读懂」能防的。**
> **只有自测用例能防。** 规格里四个用例写了期望值，一跑就现形。
> **这就是「写完补自测」的全部意义。**

### ⚠️ 顺带：那个文件是旧版快照

`compute_hit_rate` 里还是 `retrieval_map[qid]["retrieved"]`，**现在字段名是 `ranked`** → 跑起来会 `KeyError`。
**别拿这个文件当参照物。**

## 四、中途问的三个问题（都答透了）

### Q1 · `keywords` 和 `keyword_recall` 是两个不同的函数

```python
def keywords(text):                          # 1 个参数：任意一段文字 → 关键词 set
def keyword_recall(gt_answer, gen_answer):   # 2 个参数：标准答案 + 生成答案 → 分数
```

```python
gt_kw = keywords(gt_answer)                      # ← 用 keywords，1 个参数
rows.append({
    "hits": len(gt_kw & keywords(gen_answer)),   # ← 也是 keywords，1 个参数
    "total": len(gt_kw),
    "score": keyword_recall(gt_answer, gen_answer),  # ← 这里才是 keyword_recall，2 个参数
})
```

**分工：**

| 函数 | 干什么 | 输入 |
|---|---|---|
| `keywords` | **洗文字**：转小写 → 去标点 → 切词 → 去停用词 | **任意**一段文字 |
| `keyword_recall` | **算分**：命中几个 ÷ 总数 | 标准答案 + 生成答案 |

**「为什么 `keywords(gen_answer)` 里是 gen 不是 gt？」**

因为 **gt 那一侧上面一行已经洗好了**（`gt_kw = keywords(gt_answer)`）。集合交集要两边的 set，gt 侧用现成的，就只洗 gen 侧。

> ⚠️ 如果写成 `keywords(gt_answer)`，就变成 `gt_kw & gt_kw` = 它自己 → **永远返回 1.00**。
> 又是一个「分数变漂亮」的静默错。

### Q2 · `hit` 和 `hits` 不是同一个东西

| | `evaluator.py` 的 `hit()` | `keyword_recall.py` 的 `hits` |
|---|---|---|
| 侧 | **检索侧** | **生成侧** |
| 比什么 | **块编号**：`[2,0,7]` 里有没有 `[0]` | **关键词**：标准答案的词命中几个 |
| 返回 | `True` / `False` | 一个**数字**（如 `3`） |

```python
# evaluator.py —— 比编号
def hit(retrieved, relevant):
    return bool(set(retrieved) & set(relevant))     # True / False

# keyword_recall.py —— 比词的个数
"hits": len(gt_kw & keywords(gen_answer))            # 3
```

**「一个说的是『块找到了吗』，一个说的是『答案里对了几个词』。」**

**那 `hits` 为什么非要单独算？** 因为 `keyword_recall()` **只返回分数，丢掉了分子分母**：

```
keyword_recall(gt, gen)  →  0.75      ← 只有比率
                              ↑ 但打印时想显示 "3/4"
```

```python
print(f"#{r['id']:02d}  {r['hits']:>2}/{r['total']:<2} = {r['score']:.2f}  {bar}")
#                        ↑ 分子            ↑ 分母       ↑ 分数
```

**`hits`/`total` 是给人看的，`score` 才是参与平均的。**
代码注释说明这是**有意的小重复**：重复的不是**算分规则**（`/ len(gt_kw)` 仍然只有一份），只是「数一下交集的个数」。

### Q3 · ★ `retriever.py` 读 `eval_set.json`（含答案）却不作弊 —— 这是整个评测成立的前提

**事实确认：**

```python
src/retriever.py:27   EVAL_JSON = DATA_DIR / "eval_set.json"
src/retriever.py:87       full = retrieve_top_k(store, item["question"], top_k=None)
src/retriever.py:89       results.append({"id": i, "question": item["question"], "ranked": ranked})
```

**它只取了 `question`（和 `chapter` 用于打印）。从来没碰过 `item["answer"]`，也没读 `gold_chunks.json`。**

**为什么必须这样：**

评测问的是「**只给用户的问题**，能不能把装着答案的那块找出来」。

```python
# 假如这么写（作弊版）
full = retrieve_top_k(store, item["question"] + " " + item["answer"], ...)
→ 命中的那块当然排第一 → hit_rate = 1.00 → 但这个数字【什么也没说明】
```

**这叫「标签泄漏」（label leakage）** —— 评测数据里答案和输入不能混。

> **★ 最危险的地方：泄漏会让数字【变好看】**
> ```
> 正常的 bug   → 分数掉下来 → 你立刻发现
> 标签泄漏     → 分数【涨上去】→ 你以为模型变强了，还挺高兴
> ```
> **这就是它比一般 bug 更难防的原因。**

**那为什么答案和问题在同一个文件里？**
因为 `eval_set.json` 是人写的（20 题 + 标准答案 + 出处），写的时候自然挨着。

```
eval_set.json
├── id / chapter / question   ← 检索侧读这个（只读 question）
└── answer                    ← 生成侧读这个（keyword_recall 当 gt_answer）
```

**「隔离」靠的不是文件分开，而是代码的纪律：**

> **⚠️ 换句话说：这把枪在房间里，靠「没人去拿它」保平安。**
> 哪天改 `retriever.py` 时顺手加个 `item["answer"]`（想「提高召回」），
> **不报错，分数还变漂亮。**
>
> 真要做到「结构性防呆」，得把 `eval_set.json` 拆成
> `questions.json` + `answers.json`，检索侧物理上拿不到答案。
> **现在没拆，是已知的取舍**（人工写题一个文件更省事）。

**★ 已经做对的一点**：`gold_chunks.json` 是单独文件，**里面只有块编号，没有答案原文**。

```
# make_gold_chunks.py:36-41
gold.append({"id": i, "chapter": ..., "question": ..., "gold_chunks": hits})
                                                                  ↑ 只有编号 [0]
```

**这就闭合了 D1 纠正 1 那个疑问**（为什么 `evaluator.py` 不读 `chunks.json`）：

```
evaluator 需要的信息 = 「答案在第几块」= gold_chunks 的编号
                     → gold_chunks.json 里就够
                     → 它【不需要】原文，也【不该】知道答案写了什么
```

> **从检索到评测，每一环都只拿到「够用的那部分」。**

### 四的三个问题有个共同点

```
Q1  keywords ≠ keyword_recall       （名字像，不是一回事）
Q2  hit     ≠ hits                  （同一个词，两侧含义不同）
Q3  问题    ≠ 答案                  （同一个文件，只准读一半）
```

**Q3 是自己推出来的**（「chunks.json 里没有问题 → 那问题从哪来 → eval_set → 但里面有答案，这不对吧」）
—— **这个推导本身就是 D2 想练的能力。**

## 五、D3 两问答案

### A · `gold_rank()` 返回 `None` 意味着什么

> **这题的答案块，在检索排出来的整张榜单里彻底不见踪影**
> （不是「排得靠后」，是**一个都没进榜**）。

**★ 陷阱：`None` 有两条来路，函数分不清。**

```
来路 1：relevant = []        ← 这题【根本没有】gold 块可找（标注问题 = MISS）
来路 2：relevant 有编号，但一个都没出现在 ranked 里（检索彻底失败）
```

**同一个 `None`，一个是「测不了」，一个是「真失败」。光看返回值区分不了。**

> 所以 MISS 必须**单独查**（`make_gold_chunks.py` 会打印 `MISS: [...]`），
> 不能靠「`gold_rank` 是 None」反推。

### B · 为什么存 `gold_rank` 就够

> **因为 `hit@k ⟺ gold_rank ≤ k` —— 一个数就够推出任意 k 的 hit_rate。**

**9/18 那次「等字符量对比」就是活证据：**

```
那次需要：hit@2 / hit@3 / hit@4 / hit@6
总账里存：hit@1 / hit@3 / hit@5        ← 只有 @3 撞上
→ 如果只存那三个数，等字符量对比根本做不了，得把四个配置【重跑一遍】
→ 但因为存了 gold_rank，那次对比是「读数字现算」的，零成本
```

> **存原始数据，不存加工结果** —— 9/11 学的原则。
> `gold_rank` 是**事实**（第几名），`hit_rate@k` 是**从事实算出来的统计量**。
> **事实贵（要跑才有），统计量便宜（随手算）。别把贵的丢掉只留便宜的。**

## 六、三个 json 文件的作用（今天补上的）

### ① `answers_multirun.json` —— 「同一配置跑 N 轮」的答案

**它和 `answers.json` 是一对，但记录的维度不同：**

```
answers.json            每题 1 个答案   {"id":1, "answer": "..."}
answers_multirun.json   每题 N 个答案   {"id":1, "answers": ["...", "...", ...]}
```

**为什么需要它 —— 因为生成不可复现：**

```
同一问题、同样 context、temperature=0、seed=42
跑 5 次 → 能给出多种不同答案
```

**所以单个数字不可当真。** 那「多大的变化才算真改善」？**先量一量它自己晃多少**：

```
generator.py --runs 5      →  answers_multirun.json
        ↓
keyword_recall.py --noise  →  "噪声带 = [0.74, 0.77]"
        ↓
以后改动，分数要【超出这个范围】才算真改善；带内波动是抽签
```

> **一句话：它存在的唯一目的是「量出噪声有多大」，好让你知道什么时候不该激动。**
>
> **⚠️ 噪声带是【配置专属】的** —— `[0.74, 0.77]` 是 cs=800 / top_k=3 那条的。
> 换了配置必须重测，**不能沿用**。

### ② `chunk_config.json` —— 「这批块是哪套参数切的」

```json
{"chunk_size": 800, "chunk_overlap": 160, "n_chunks": 114}
```

**为什么不能从 `chunks.json` 推？**

```
chunks.json 里只有： [{"index":0, "text":"..."}, {"index":1, "text":"..."}, ...]
                            ↑ 只有内容和顺序，【没有】"我是 400 还是 800 切的"
```

**「我是 800 切的」这个事实，一旦 `chunker.py` 跑完就消失了** —— 除非有人记下来。

### ③ `gen_config.json` —— 「这批答案是哪套参数生成的」

```json
{"top_k": 3, "runs": 1, "model": "qwen-plus"}
```

**同一个思路换到生成侧，而且它是【被 bug 逼出来的】：**

```
9/18 那个静默 bug：
  evaluator 的 key     ：(cs, overlap, top_k, side)
  keyword_recall 的 key：(cs, overlap, side)      ← 漏了 top_k
  → top_k=3 和 top_k=6 的 key 撞车，后跑的覆盖先跑的

修法：generator.py 盖章（写 gen_config.json）
      keyword_recall.py 读章、合并进 config、key 对齐
```

### 三者一起看

| 文件 | 谁盖章 | 章上写什么 | 谁读它 |
|---|---|---|---|
| `chunk_config.json` | `chunker.py` | cs / overlap / n_chunks | `evaluator.py` + `keyword_recall.py` |
| `gen_config.json` | `generator.py` | top_k / runs / model | `keyword_recall.py` |
| `sweep_results.json` | 两个计分脚本 | 章 + 成绩 + 逐题明细 | **人（你）** |

> **前两个是「图章」，第三个是「账本」。**
> 图章不参与加工，只让产物**能自证身份**；账本把章和成绩订在一起。

**★ 用这个结构就能回答一个关键问题：**

```
问：sweep_results.json 里那条记录的 config 字段，是从哪来的？
答：不是 evaluator 自己知道的 ——
    是它【读 chunk_config.json（chunker 盖的章）】+【读 gen_config.json（generator 盖的章）】
    拼出来的。
    → 所以它记下的配置【不可能记错】，因为它从没"凭记忆"写过。
```

## 七、`answers_multirun.json` 的 51% 重复 —— 正常现象

**实测：**

```
20 题 × 5 轮 = 100 个答案，不同的只有 49 种  →  重复率 51%
其中 8 题（#01/03/04/05/09/11/14/15）5 轮答案【完全相同】
```

### 为什么正常

```python
temperature=0,   # 最尖的分布
seed=42,         # 钉死随机序列
```

**`seed` 让随机序列每次都从同一个起点跑 → 很多题就复现了。种子就是这个作用。**

**那为什么还有一半不一样？**

> **因为 `seed` 管不住所有东西。** 大模型服务端有**并行/批处理** ——
> 同批请求被拆到不同机器、不同批次里算，**浮点累加顺序会变**。
> 差一点点，就可能在某个词上「翻过山头」，选到另一个词。

**这正好解释了 9/18 log 那句话为什么两半都对：**

```
「生成不可复现（6 次跑出 5 种答案）」   ← 说的是 #08 / #13 这类题
「8 题 5 轮全同」                      ← 说的是 #01/03/04/... 这类题
```

### ★ 更重要：噪声**不在文字层，在分数层**

```
第 1 轮：0.748
第 2 轮：0.737
第 3 轮：0.770
第 4 轮：0.749
第 5 轮：0.740

噪声带 = [0.74, 0.77]     波动只有 0.033
```

**文字层重复率 51%，分数层波动 0.033。** 为什么？

```
#01：5 轮答案【只有 1 种】            → 分数 5 轮都是 1.00，波动 0.00
#10：5 轮答案【有 2 种】但只是措辞不同 → 分数 5 轮都是 1.00，波动 0.00
```

**大模型改写措辞（换连接词、调语序），但关键词没变 → `keyword_recall` 测的是关键词，所以分数不动。**

> **这就是「噪声带 = 晃动范围」的真实含义 ——**
> **它量的不是「答案像不像」，是「分数动不动」。**
> **对调参来说，只有后者有意义。**

**而且这是个好消息**：噪声带窄（0.033），意味着**微小的真实改善也能被检测出来**。
如果 5 轮在 0.70~0.90 之间乱跳，这个指标就没法用了。

└───────────────────────────────────────────────────────────────┘
```

### ★ 两条要特别注意的边

**边 1：`keyword_recall.py` 有【两个完全不同的模式】**

```cmd
python src/keyword_recall.py            → 读 answers.json          → 出分数（可 --record）
python src/keyword_recall.py --noise    → 读 answers_multirun.json → 出噪声带（不写文件）
```

**同一个脚本，两个入口，读不同文件，产出不同性质的东西** —— 和 `retriever.py` 的 `--rebuild` 是同个模式。

> **⚠️ 所以 `answers_multirun.json` 在图上是【孤立的分支】：**
> 它只喂给 `--noise`，产出的东西**不进入任何文件**。
> 它和 `answers.json` 是**兄弟，不是上下游** —— 用途不同，互不依赖。

**边 2：噪声带【不进账本】**

```
噪声带 [0.74, 0.77]  →  只打印在屏幕上  →  你自己记住 / 写进 log
                     →  【没有】写进 sweep_results.json
```

**这是设计取舍**（噪声带是配置专属的，而且它回答的是「这次改动算不算数」，是**人工判断的参考值**，不是一条记录）。

> **⚠️ 但这也意味着一个风险**：噪声带**没有存盘**。
> 换配置重测一个，前一个就只留在 log 或记忆里了。
> **配置多了之后，它可能需要被记进账本**（挂到 `config` 上当一个字段）。

### 一句话总结三条链

```
① 内容链：txt → chunks → retrieval → answers          （东西被加工）
② 生成侧双分支：answers.json（单次分数）/ answers_multirun.json（噪声带）
③ 图章链：chunk_config / gen_config                   （产物自证身份）
④ 账本：sweep_results                                 （章 + 成绩订一起）
```

## 九、⚠️ 脚本安全性检查（今天顺手做的）

**起因**：担心「跑手写脚本会不会覆盖 `data/` 里的结果」。查完发现风险图是这样的：

| 手写脚本 | `DATA_DIR` 指向 | 写操作 | **跑起来会怎样** |
|---|---|---|---|
| `chunker-手写.py` | `大二/data` ← **不存在** | 5 处 | 💥 **读文件就崩，走不到写** |
| `make_gold_chunks-手写.py` | `大二/data` ← **不存在** | 3 处 | 💥 同上（还读 `chunks_me.json`） |
| `retriever-手写.py` | `大二/data` ← **不存在** | 4 处 | 💥 同上 |
| `keyword_recall-手写.py` | ✅ 真实 data | **0 处** | ✅ 安全 |
| `evaluator-手写.py` | ✅ 真实 data | **0 处** | ✅ 安全 |
| **`generator-手写.py`** | ✅ 真实 data | **2 处** | ⚠️ **会覆盖 `answers.json`，还要花 API 钱** |

**★ 真正危险的是 `generator-手写.py`，不是 `evaluator-手写.py`。**

**前三个之所以安全，是因为【写错了路径】**（`大二/data` 根本不存在，在「读」那一步就崩了）
—— **安全是巧合，不是设计**。哪天路径修对了，它们立刻变成真危险。

> **这就是 D2 那两列的实战版：**
> ```
> A：跑起来会【写】吗？        → 看有没有 json.dump
> B：写的话，写到【哪】？      → 看 DATA_DIR 指哪
> ```
> **两个都是「危险」答案，才构成真正的风险。**
> 以后运行任何脚本前，这两问值得花 10 秒问一遍。
