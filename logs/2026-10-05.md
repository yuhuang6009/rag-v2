### 3.1 bug ① / bug ② —— 自测全绿，代码却是错的

**bug ① `3_keywords.py`**：正则写成了 `[^a-z0-9/s]`

```
应该是 \s（反斜杠 s = 空白）          实际是 /s（斜杠 + 字母 s）
→ 斜杠没被当分隔符清掉，留了下来

实测：keywords("and/or")  →  {'and/or'}    （错）
      正确应该是          →  set()
```

**为什么自测没抓到**：6 个测试用例**没有一个含斜杠**。
→ **测试通过 ≠ 代码正确。用例没覆盖到的地方，绿也是假的。**

**bug ② `4_keyword_recall.py`**：`len(gen_keywords&gt_keywords)` —— **`&gt` 中间没有空格**

```
Python 不认 &gt 是转义，它解析成：  gen_keywords  &  gt_keywords
                                    ~~~~~~~~~~~~     ~~~~~~~~~~~~
                                    Name            Name
                                    = 按位与（BitAnd）

→ 它能跑通，纯粹因为第 32 行那个变量刚好叫 gt_keywords。
  换个名字（gt_kw）就是 NameError。**这不是「与」的意思，是巧合。**
```

（顺手还标了一行死代码：`# return score if score is not None else None` —— 永远不会执行。）

### 3.2 第 6 题两处「碰巧对」（行为对，但意图不清晰）

```
① for...else 用错了地方 —— 这里碰巧对
   你写 for i in range(...): ... else: return None
   Python 的 for...else = 「循环没被 break 打断、正常跑完就执行」，
   不是「没找到就……」。你循环体里没有 break → else 必然执行 → 恰好等于
   「循环走完返回 None」。对了，靠巧合。
   建议：for i, idx in enumerate(ranked, 1): ... ; return None（循环外）

② 多 gold 取最好名次 —— 也碰巧对
   你返回「第一个撞上的」；因为从头往尾扫，第一个撞上的必然是排名最靠前的。
   源码用 min(ranks) 是【显式】说「取最小」，意图更清楚。
```

**这两处不算错，但值得记**：**「对」有两种 —— 想对了，和碰巧了。**
闭卷默写时碰巧对，考场上（或改个数据）就可能翻车。

## 四、★ 第 9 题（`_check_stamp`）为什么 2/4 —— 两个 bug

```
[FAIL] 戳和产物全对 → 放行      期望 通过，得到 拒绝
[OK]   runs 对不上 → 拒绝
[OK]   top_k 对不上 → 拒绝
[FAIL] 戳文件不存在 → 拒绝      期望 拒绝，得到 <FileNotFoundError>
```

### bug ①   第 46 行 `if not GEN_CONFIG_JSON:`

```
想的是「这个戳文件【在不在】」，
问的是「这个 Path 对象【是不是空的】」—— 而 Path 对象【永远是真值】：

    >>> bool(Path("不存在的文件.json"))
    True                          ← 永远 True，哪怕文件不存在

→ if 永远不成立 → 不退出 → 直接 json.load(open(...)) → 文件不存在 → FileNotFoundError
   （而不是我们想要的「拒绝」）

改法：  if not GEN_CONFIG_JSON.exists():
```

### bug ②   第 55 行 `stamp.get("top_k") != _data_top_k`

```
忘了调用 _data_top_k，拿【函数本身】去比：

    stamp.get("top_k")   !=   _data_top_k
    2                    !=   <function ...>     ← 永远不等

→ 每次都往 problem 里塞一条 → 永远拒绝记账 → 把「全对 → 放行」那条也误伤了。

改法：  if stamp.get("top_k") != _data_top_k(records):
```

（小毛病：top_k 分支的报错信息里写成了 `runs:`，应是 `top_k:` —— 报错信息写错字段名，真出事时会把人带偏。）

### ★ 这两个 bug 是同一个族：**「问的问题，和你以为问的问题，不是一回事」**

```
bug ①   想问「文件在不在」，问成了「对象是否为空」
bug ②   想问「top_k 等不等于 2」，问成了「等不等于那个函数」
```

跟第 3 题的 `/s`、第 4 题的 `&gt` **完全同一类** —— **代码能跑，但意思不是你想要的。**

## 六、★★ 这两天的同一个主题：**结论对 ≠ 理由对**

把 9 个 bug / 失分点摊开看，**全是同一个形状**：

```
默写侧                      概念侧
─────────────               ─────────────
3  /s        代码能跑≠意思对   5  用字数猜 prompt（结论对，理由错）
4  &gt        代码能跑≠意思对   7  说数值大小（问的是波动）
9① 对象是否为真（不是文件）    8  把结论当盲区
9② 函数对象（不是数值）        9  没给数，只给定性解释
─────────────               ─────────────
= 测试通过 ≠ 代码正确          = 结论对 ≠ 理由对
```

**两条其实是同一条：**

> **一个「检查 / 结论」自己，没有被检查过。**
>
> · 自测全绿 → 你以为代码对了 → **但用例没覆盖到那个分支**（bug ①②）
> · 结论说得出 → 你以为懂了 → **但拿不出证据、只能讲感觉**（第 7/8/9 题）
>
> 跟 9/29 那次「说写了其实没写」、跟 10/3 我拿错前提做检查，
> **是同一个族，这是第 N 次了。**

**→ 具体动作（就两句）：**

```
① 写完任何检查逻辑，先喂一个【你知道答案】的输入（正对照 + 负对照）。
② 说任何一个结论，先问：「我是【数出来 / 读字段】得到的，还是【猜 / 讲道理】得到的？」
   猜的 → 证据还没到手 → 别下结论。
```
