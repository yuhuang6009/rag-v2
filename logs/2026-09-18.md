## 二、★ 今天最重要的发现：一个静默 bug

### bug 长什么样

`evaluator.py` 和 `keyword_recall.py` 各有一个 `_sweep_key`，**逐字对比**：

```python
# evaluator.py（对的）
return (c.get("chunk_size"), c.get("chunk_overlap"), c.get("top_k"), entry["side"])

# keyword_recall.py（修之前 —— 漏了 top_k）
return (c.get("chunk_size"), c.get("chunk_overlap"), entry["side"])
```

### 后果（我实测了）

```
生成侧 top_k=3 的 key: (800, 160, 'generation')
生成侧 top_k=6 的 key: (800, 160, 'generation')
一样吗？ True     ← 撞车！后跑的覆盖先跑的
```

**`top_k` 决定「喂几块给大模型」→ 直接决定生成什么答案 → 是两条不同的记录。但它们的 key 一模一样。**

**而且完全静默** —— 不报错、不警告，只是数据悄悄少了一条。

**修法**：`generator.py` 新增写 `gen_config.json`（记录 `top_k`/`runs`/`model`），
`keyword_recall.py` 读它并合并进 config，同时把 `_sweep_key` 对齐。

### 为什么这个 bug 值得记

**因为两个函数单独看，每一个都能读懂。**

```
evaluator 那个：4 个字段，清楚
keyword_recall 那个：3 个字段，也清楚
```

**→ bug 不在函数里，在「两个函数之间」。**

| | 能读懂 | 能发现这个 bug |
|---|---|---|
| 看的是 | 一个函数内部 | **两个函数的关系** |
| 问的是 | 「这行干什么」 | **「这两处说的是一回事吗」** |
| 能力 | 阅读理解 | **一致性检查** |

> **「能读懂」是局部能力。而 bug 住在局部之间。**

## 三、代码分三类，标准不同

| 类 | 例子 | 标准 |
|---|---|---|
| **① 核心算法** | `keywords()` / `cosine_similarity()` / `chunk_text()` / `keyword_recall()` / `hit()` | ★ **必须能闭卷默写** |
| **② 数据搬运/记账** | `record_sweep()` / `_sweep_key()` / `int_arg()` / 路径常量 / `json.dump` | **能读懂 + 能改** |
| **③ 一次性胶水** | print 格式、`enumerate(x,1)` | **看不懂就查，不用记** |

**为什么 ② 类是「能改」而不是「能默写」**：

- **① 类是知识**：`precision@k = recall@k × (gold/k)` —— **忘了就真不会了**
- **② 类是手艺**：往 JSON 列表里 upsert —— **忘了看 5 分钟文档就能写**，而且每个项目写法都不同（SQL / CSV / JSON）

**没有工程师会背「怎么 upsert」。但他会认出「这里需要 upsert」，然后 3 分钟写对。**

### ② 类里唯一值得记的思想：upsert

```python
sweep = [e for e in sweep if _sweep_key(e) != key]    # 同身份 → 删旧
sweep.append(entry)                                    # 再加新
```

**「同一个就更新，新的就新增」** —— 数据库的 `INSERT ... ON CONFLICT`、缓存更新、配置合并，全是它。

**而真正的考点是那个问句：**

> ### ★「什么算『同一个东西』？」

**`_sweep_key` 的正确含义 =「所有能改变这条记录的输入」**

- **少了** → 本该分开的记录撞车（我今天犯的错）
- **多了** → 本该合并的记录被拆开

**自测题（明天想）**：如果要记录 **prompt 模板版本号**，三个文件分别要不要改？
<details>答案：`generator.py` 要记录它；`keyword_recall.py` 的 key 要加它（prompt 影响生成结果）；
**`evaluator.py` 的不加** —— 检索跟 prompt 无关。答成「两个都加」= 还没理解 key 的含义。</details>

## 四、新增代码说明（明天细读）

### `chunker.py` · `int_arg(name, default)`

**把配置从「源代码的一部分」变成「输入」。**

```python
def int_arg(name, default):
    for i, arg in enumerate(sys.argv):
        if arg == name:                          # --chunk-size 400（空格隔开）
            return int(sys.argv[i + 1])
        if arg.startswith(name + "="):           # --chunk-size=400（等号连着）
            return int(arg.split("=", 1)[1])
    return default
```

**核心概念：**

- **`sys.argv`** = 你敲的命令，按顺序装成一个 **list**，**全是字符串**
  ```
  python src/chunker.py --chunk-size 400
  → sys.argv == ['src/chunker.py', '--chunk-size', '400']
  ```
  - 第 1 个元素**永远是脚本自己** → 真参数从索引 1 开始
  - **没敲参数时不是空的**，是 `['src/chunker.py']`（长度 1）

- **`enumerate(sys.argv)`** = 「数着数遍历」，同时拿到**位置 `i`** 和**元素 `arg`**
  （你之前用过 `enumerate(eval_set, 1)`，那个从 1 开始，这个默认从 0）

- **`sys.argv[i + 1]`** = 整个函数的灵魂
  ```
  ['src/chunker.py', '--chunk-size', '400']
        i=0            i=1            i+1=2  → '400'
  ```
  **「选项名排第 i 位，值就排第 i+1 位」**（因为空格隔开）

- **`split("=", 1)` 的 `1` = 最多切 1 刀** → 保证切出 2 段，`[1]` 稳定拿到「等号后面的全部」
  ```python
  'a=b=c'.split("=")     → ['a','b','c']    ← 3 段
  'a=b=c'.split("=", 1)  → ['a','b=c']      ← 2 段
  ```

- **`return default` 的缩进是关键** —— 它在 `for` **外面**，所以循环跑完才执行
  ```python
  for ...:
      return ...      # 找到 → 立刻返回，函数结束
  return default      # 循环跑完都没 return → 没找到 → 用默认值
  ```
  **「找到就返回」和「没找到用默认值」靠缩进自然分开，不需要额外的标志变量。**

- **`CHUNK_SIZE = 800` 常量没删** —— 从「唯一真相」降级成**默认值**

### `chunk_config.json` · `gen_config.json` · `sweep_results.json`

```
chunker.py    → chunk_config.json   {chunk_size, chunk_overlap, n_chunks}
generator.py  → gen_config.json     {top_k, runs, model}
                   ↓ 被抓取
evaluator.py / keyword_recall.py  → record_sweep() → sweep_results.json
```

**为什么要多这些文件**：`chunks.json` 里只有 `[{"index":0,"text":...}]` —— **没有「我是 400 切的」这个信息**。下游记分时**无从得知配置**。

> **每个脚本给自己盖一个章，记账的负责收集所有章。读结果的人不用在命令行重复报配置，也不会记错。**
> **这就是「可追溯」** —— 每个产物都要能说出自己是怎么来的。

### `_sweep_key(entry)` —— 回答「这条记录是谁？」

**输入**一条记录，**输出**一个元组（身份），如 `(400, 160, 3, 'retrieval')`

**为什么单独成函数：**
1. 被用了两次（算 key、比较 key）
2. ★ **`evaluator.py` 有个同名的，必须一致** —— 写成命名函数，**这个概念才有名字、能被对比**

> **⚠️ 已知取舍**：两份代码需要手工保持一致。**更好的做法是抽到公共模块 import。**
> 暂时没抽是因为这两个文件还是「脚本级」的。**这不是最佳实践，是已知的技术债。**

> **⚠️ `.get()` 是静默的**：字段缺失返回 `None`，**不报错**。
> 两条「都没记录 top_k」的记录会互相覆盖且完全静默 —— **和我今天那个 bug 是同一类问题**。

### `record_sweep(avg, rows)` —— 记一笔账

```python
# ① 攒配置（生成侧要合并两个文件）
config = json.load(open(CONFIG_JSON)) if CONFIG_JSON.exists() else {}
if GEN_CONFIG_JSON.exists():
    config.update(json.load(open(GEN_CONFIG_JSON)))

# ② 组装
entry = {"config": config, "side": "generation",
         "metrics": {"keyword_recall": avg}, "per_question": rows}

# ③ upsert
sweep = json.load(open(SWEEP_JSON)) if SWEEP_JSON.exists() else []
sweep = [e for e in sweep if _sweep_key(e) != _sweep_key(entry)]
sweep.append(entry)

# ④ 写回
json.dump(sweep, open(SWEEP_JSON, "w"), ensure_ascii=False, indent=2)
```

**`side` 必须存在** —— 否则同一配置的检索侧和生成侧会撞车。

**签名为什么是 `(avg, rows)`** —— 调用者手上已经有这俩了：

```
compute_keyword_recall(eval_set, answers)
    → return avg, rows
             ↓      ↓
      record_sweep(avg, rows)
             ↓      ↓
          metrics  per_question
```

**它不重新算分，也不自己读 `answers.json`** —— **又是「函数收数据不收文件名」+「算分规则只有一份」。**

### ★ `per_question` 里只存 `gold_rank`（最有用的一处）

```python
"per_question": [{"id": qid, "gold_rank": ...} for qid in gold_map]
```

**因为 `hit_rate@k` 可以从 `gold_rank` 推出来**：`hit@k  ⟺  gold_rank ≤ k`

**实测验证：**
```
从 gold_rank 反推：      记录里的：
@1 = 0.60                @1 = 0.6  ✓
@2 = 0.85
@3 = 0.90                @3 = 0.9  ✓
@4 = 0.95
@5 = 1.00                @5 = 1.0  ✓
```

**→ 「等字符量对比」不用重跑任何东西**（读 `gold_rank` 现算）

> **存原始数据，不存加工结果** —— 9/11 学过的原则，今天用上了。
> **`@5 = @6 = @8 = 1.00`** → 最差的 gold 排第 5 名 = 「病因是排序不是召回」的量化证据。

## 五、MISS 是什么

> **MISS = 某题的标准答案没能完整落进任何一块** → `gold_chunks` 是空列表 `[]`

### 为什么会发生

`make_gold_chunks.py` 是**子串查找**：

```python
hits = [idx for idx, cn in chunk_norm if ans in cn]
#                                        ↑ 「标准答案」是不是「整块文字」的一部分
```

**答案正好跨在块的边界上：**

```
原文： ...三个主因是【化石燃料燃烧、森林砍伐、工业排放】...
                  ↑ 块5 结束          ↑ 块6 开始

块5尾： ...三个主因是化石燃料燃烧、
块6头： 森林砍伐、工业排放...

标准答案 = "三个主因是化石燃料燃烧、森林砍伐、工业排放"
→ 块5 里没有（少后半）   → 块6 里没有（少前半）   → hits = []  ← MISS
```

### ★ 为什么 MISS 会让对比失效

```python
return hit_count / len(gold_map)     # 分母恒等于 20，不管有几题 MISS
```

```python
hit(ranked[:top_k], relevant)        # relevant = [] → 交集恒为空 → False
# → 这题永远判 MISS，无论检索多准
```

```
cs=800  MISS=0  →  20 题全部可测  →  hit_rate@3 = 0.90
cs=400  MISS=4  →  16 题可测 + 4 题注定失败  →  hit_rate@3 = 0.80
                              ↑ 你以为「检索变差了 0.10」
                                实际 4/20 = 0.20 是「题本身测不了」
```

**两个数不是同一个东西 —— 一个测 20 题，一个测 16 题，分母却都是 20。**

> **MISS 本身不是代码 bug，是「评测集设计」的必然代价**：
> 标准答案必须是**原文的连续片段**且**长度 < chunk_size**（`评测集设计指南.md` 的规矩）。

**实测的长答案**：`#07 = 305 字符`（最长），中位 141 → **chunk_size 的硬下界由最长标准答案决定**。

## 六、路线 A / B —— 选哪套「chunk_size + overlap」组合

### 路线 A：overlap 占比固定 20%

```
(400,80)(600,120)(800,160)(1200,240)
```
✅ **只有一个变量在变**（单变量原则）
❌ **MISS 不为 0**：cs=400/ov=80 → 4 题 MISS，cs=600/ov=120 → 1 题
   **→ 前两个配置的分数不可比**

### 路线 B：MISS 全为 0 ★ 今天选这个

```
(400,160)(600,180)(800,160)(1200,240)
overlap 占比：40% / 30% / 20% / 20%
```
✅ **四个配置全部可测** → 对比有效
❌ **两个变量一起变**（cs 和 overlap 占比）→ 归因不确定，需在日志注明

### 为什么选 B

| | 后果 | 能补救吗 |
|---|---|---|
| **MISS>0** | 分数**根本没有意义**（分母错） | ❌ 不能 |
| **多一个变量** | 分数有意义，但**归因不确定** | ✅ 日志注明即可 |

> **「能比但不完美」好过「根本不能比」。**

**而且**：这个实验的核心问题是「chunk_size 是不是瓶颈」。**B 恰好保住了「cs=400 也能不丢答案」这个最重要的发现** —— A 直接把 cs=400 判了死刑。

### 还有第三条路（今天不做）

**「只在两个配置都测得到的题上对比」** —— 因为 `per_question` 存了 `gold_rank`（MISS 的是 `None`），可以**事后离线算**，两个配置用同一个分母。

**好处**：既保住 overlap 占比固定，又保住可比。
**代价**：分数不再是「20 题的分数」，是「N 题的分数」，且 N 可能每次不同，解释成本高。
**→ 等结果出来如果「多变量」真的影响结论了，再回来用这条。**

## 七、⚠️ 扫参的完整流程（四步，一步都不能少）

**这是今天才理清的 —— 我一开始漏了第 2 步。**

```cmd
python src/chunker.py --chunk-size 400 --overlap 160   ← ① 切块
python src/make_gold_chunks.py                          ← ② ★ 必须重跑
python src/retriever.py --rebuild                        ← ③ 重算向量 + 排名
python src/evaluator.py --record                         ← ④ 记分
```

**为什么第 2 步不能漏**（实测证明）：

```
cs=800 的 gold：  [0] [2] [2] [3] [9]  [14] [15] [15] [25] [32] ...
cs=400 的 gold：  [1] [6] [7] [9,10] [24] [38] [41] [42] [66] [86] ...
```

**全部变了** —— 因为 gold 是「答案落在**第几块**」，块变了编号当然全变。

**漏了会怎样**：拿 cs=400 的 `retrieval_results`（编号 0~301）去比 cs=800 的 `gold_chunks`（编号 0~113）→ **编号对不上 → hit_rate 是垃圾数字**。

> **这就是「可追溯」在实战里的样子**：一个产物变了，**下游所有依赖它的产物全部失效**。

| (600, 180) | 173 | 0.80 | 0.85 | 0.90 | 1.00 |
| (800, 160) ← 基线 | 114 | 0.60 | 0.85 | 0.90 | 1.00 |
| (1200, 240) | 76 | 0.60 | 0.90 | 0.95 | 1.00 |

**三个立刻能读出来的事实：**

1. **`hit@5` 四个配置全是 1.00** → 没有任何一题「检索不到」，**全是排序问题**（再次印证 9/13 的诊断）
2. **`(400,160)` 是唯一 `hit@2 = 1.00` 的** → 只有它做到「20 题答案全部排进前 2 名」
3. **基线 (800,160) 的 `hit@1 = 0.60` 是全场最低**（与 1200 并列）
   → 800 **不是个好选择，只是「没 MISS 的最小值」**（第一周我是被 MISS 逼到 800 的）

### ② 这个胜利不是「槽位多」的假象

`choose_chunk_size` 踩的坑（固定 top_k=5 → 大块白拿更多文本 → 比较不公平）。
用**等字符量**再比一次：

| 配置 | top_k | 名义字符 | 命中率 |
|---|---|---|---|
| **(400, 160)** | 6 | 2400 | **1.00** |
| (600, 180) | 4 | 2400 | 0.90 |
| (800, 160) | 3 | 2400 | 0.90 |
| (1200, 240) | 2 | 2400 | 0.90 |

**喂同样多的文本，(400,160) 仍是唯一的 1.00 → 它的优势不是「拿得多」，是「每一块更准」。**

> ⚠️ 严格说「名义 2400 字符」≠「2400 个不重复字符」：块相邻时 overlap 会重复。
> cs=400 top-6 若相邻只剩 1600 个不重复字符，cs=800 top-3 有 2080
> —— **即它用更少的实际文本拿到更高的命中**。
> 但检索出的块未必相邻，所以这条只能算「不削弱结论的旁证」，**不当主证据**。

### ③ ★ 分歧全压在两题上：#07 / #08

| 题 | cs400 | cs600 | cs800 | cs1200 |
|---|---|---|---|---|
| **#07** | **2** | 5 | 5 | 4 |
| **#08** | **2** | 5 | 4 | 1 |
| 其余 18 题 | 全 ≤ 2 | 全 ≤ 3 | 全 ≤ 3 | 全 ≤ 3 |

**其他 18 题几乎不动（都在 1~2 名）。`0.90 → 1.00` 的全部差距，就是这两题。**

### ④ 病因找到了：跨章节「缝合块」

`#07` / `#08` 的答案都在 **Chapter 4 开头**，而 Chapter 3 结尾讲海洋生态
—— **两章的交界正好落在块的中间**。

**实测：这两题的答案在三个 cs 下分别落在哪：**

| cs | 落在第几块 | **块开头是什么** | 块内**非**答案字符 | 答案占块 |
|---|---|---|---|---|
| 400 | #07→41 / #08→42（**分开了**） | 「…protected areas are vital. **Chapter 4:**…」 | 95 / 262 | **76% / 35%** |
| 800 | #07→15 / #08→15（**同一块**） | 「the health and survival of various **marine species**…」 | 495 / 662 | 38% / 17% |
| 1200 | #07→10 / #08→10（**同一块**） | 同上（marine species） | 895 / 1062 | 25% / 12% |

**看「块开头」那一列 —— 这是全部的答案：**

```
cs=800 / 1200 的同一个块：
  ┌─────────────────── 一块 800~1200 字符 ───────────────────┐
  │ 海洋物种…（Ch3 结尾） │ ← 305 字符 →  │ #07答案 │ …  │ #08答案 │
  └──────────────────────────────────────────────────────────┘
   ↑ 块从 Ch3 中间切进去 → 开头的「海洋物种」把整块向量往生态话题拽

cs=400 切成两块：
  第 41 块： [protected areas are vital.] [Chapter 4: … #07答案 …]   ← Ch3 只剩 68 字符
  第 42 块： [adaptation involves … #08答案 …]                       ← 纯 Ch4
```

**机制**：一个块的向量 = **块内所有文字的语义平均**。

- 块里混了**两个话题**（海洋生态 + 气候适应）→ 向量指向**两者的中间**
  → 跟「气候适应」的问题**就没那么像了**
- 块小 → 切得细 → 每块**话题更纯** → 向量更尖 → 排得更高

> **这不是我编的解释 —— 两个独立证据：**
> ① 答案占块比例（38% → 76%）和名次（5 → 2）**同向变化**（1200 也符合：25% → 4）
> ② **你 9/13 逐题诊断 #7/#8 时，已经独立得出过「#15 是跨章节缝合块」**
>    —— 当时只看出「块跨了章节」，**今天量化了它为什么伤害排序**

**⚠️ 一个解释不了的点（必须记下，不编故事）**：
`#08` 在 **cs=1200 排到第 1 名**，虽然答案只占那个块的 **12%**。
按「越纯越好」它该排得最差。**这条不符合上面的机制。**
（猜测：cs 越大块越少，竞争者从 302 降到 76，「排前面」本身变容易 —— **但这是猜测，没验证。**）

### ⑤ 这个结论有多硬？（诚实标注）

| 威胁 | 影响 | 为什么仍能下结论 |
|---|---|---|
| **路线 B 的 overlap 占比不固定**（40/30/20/20%） | 归因不纯 | 分歧只在 #07/#08，而缝合块机制**跟 overlap 无关**，只跟「块边界落在哪」有关 |
| **MISS** | 无 | 四配置 **MISS 全部 = 0**（这就是选 B 换来的） |
| **多 gold 题** | cs=400 有 3 题（#04/#17/#18）、cs=600 有 1 题、cs=800 有 0 题 | 那 3 题在 cs=400 下**全是第 1 名** → 不是靠「多 gold 更容易撞上」捡的分 |
| **块数不同 → 竞争强度不同** | 未量化 | 方向上对 cs=400 **不利**（302 个竞争者 vs 1200 只有 76 个）→ **它还是赢了，结论只强不弱** |

### ⑥ 所以第 7 周检索侧的结论

**`chunk_size` 从 800 换成 400：`hit@3` 0.90 → 1.00，而且 `hit@2` 也是 1.00。**

对生成侧的含义：

```
基线   ： top_k=3 × 800 字符 = 2400 字符 喂给大模型
新配置 ： top_k=2 × 400 字符 =  800 字符 喂给大模型    ← 文本量 1/3，命中率还更高
```

> **更少的 token、更便宜、更快，而且更准。** 这正是 `choose_chunk_size` 想找的那类结果。

**代价**：块数 114 → 302（存储 + 候选变多）。但检索是本地算余弦，**不花钱**。

**⚠️ 下一轮必须验证的点**：生成侧要确认「只喂 800 字符，大模型够不够答对」——
**理论上够，但如果 `keyword_recall` 掉了，说明「检索更准」被「上下文太少」抵消了。**
**这就是为什么生成侧必须真跑，不能拿 `hit_rate` 代表一切。**
